# BARLOVENTO — Technology

## Engine

- **Godot 4.7.2-stable** — the latest stable release as of **2026-10-13**.
  - Godot 4.8 is still in development (dev builds); do **not** target it.
  - Godot 3.x and 4.5-and-earlier are out of scope.
- **Language:** GDScript.
- **Rendering:** Forward+.
- **3D:** true 3D combat with a free camera. Movement is vector-based
  (Newtonian).

## Development model

The project is developed **100% by LLM agents**. Consequences:

- Everything must be reproducible from text: GDScript, `.tscn` scene files,
  docs, and image prompts.
- **No human artist.** Art is generated by the art-director agent via the
  `agy` CLI (Gemini). See `docs/art/ART_DIRECTION.md`.
- Prefer data-driven, modular systems (managers + resources) over monolithic
  scenes.

## Architecture (planned)

The game has two combat phases and a strategic layer, so keep them separate:

- **Strategic layer** — campaign map, the Calm front, fleet/roster
  management.
- **Admiral phase** — simultaneous movement planning + resolution.
- **Ace phase** — turn-based tactical combat.
- **Shared simulation core** — the Newtonian movement/inertia model used by
  both combat phases.

Proposed autoloads/services (Godot singletons):

| Autoload | Responsibility |
| --- | --- |
| `Game` | top-level state machine (strategic ↔ admiral ↔ ace) |
| `TurnManager` | phase orchestration, order resolution, initiative |
| `PhysicsSim` | vector movement, inertia, éther currents |
| `FleetManager` | ship/hero roster, persistence |
| `LoreDB` | factions, ships, heroes, weapons (data-driven) |

This is a *proposed* structure; implement in small, verifiable increments.

## Movement / inertia math

- Each ship: `position`, `velocity`, `mass`, `facing`, `max_speed`,
  `max_thrust`, `brake_thrust`, `turn_power`.
- Integration: `velocity += (thrust/mass) * dt; position += velocity * dt`.
- Orders are a **target velocity** (`target_speed`, `target_heading`), not raw
  throttle. Per step `dt`:
  1. Rotate `facing` toward `target_heading` by at most `(turn_power/mass)*dt`.
  2. If `|velocity| < target_speed`, accelerate along `facing` by
     `(max_thrust/mass)*dt`; if above, brake along `-velocity` by
     `(brake_thrust/mass)*dt`. Clamp `|velocity|` to `[0, max_speed]`.
  3. Add the éther current gradient to `velocity`.
  4. `position += velocity * dt`.
- `dt` is fixed-timestep during resolution; the Admiral phase advances a
  fixed window of simulated seconds; the Ace phase advances in discrete
  actions mapped onto the same simulator.
- Éther currents are local gradient vectors added to `velocity` (strength
  depends on faction and current).

## Combat (Ace phase)

- The Ace phase is turn-based unit activation: ships are queued (player then
  enemy) and each activation grants a fixed action budget (default 2 AP).
- **Move** advances the active ship a fixed window of simulated seconds using
  the same `PhysicsSim` integrator; **Shoot** resolves damage against a target.
- A target is hittable when within `weapon_range` **and** inside the shooter's
  forward firing arc (`weapon_arc_degrees`, a cone around `facing`).
- Damage reduces `hp`; a ship at `0` hp is destroyed and removed from the queue.
- Per-facing armor and subsystem targeting are deferred; all ships currently use
  a single forward arc.

## Asset pipeline

- Generate images with `tools/gen-image.sh` (wraps `agy`). Prompts live in
  `docs/art/prompts/` and are the source of truth.
- Import generated art into `assets/` following `assets/README.md`.

## Environment

- `GEMINI_API_KEY` — Gemini API key used by `agy` (headless/CI).
- `AGY_BIN` — optional override for the `agy` binary path.

## Verification

```bash
godot --headless --path . --quit          # project parses and loads
godot --headless --path . --import        # import assets
```

Run these after structural changes. Gameplay verification needs a human/agent
running the editor until an automated test setup exists.
